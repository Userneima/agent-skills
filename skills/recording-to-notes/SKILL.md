# 从录音到笔记

一段录音走到成品要经过六件事：**看素材 → 剪空白 → 源文件进回收站 → 转写 → 写笔记 → 出 PDF**。

这份 skill 的价值不在流程本身（流程很直白），而在**每一步都有一个静默失败的坑**——它不报错，只是给你一个看起来正常的坏结果。下面每条约束都对应一次真实的失败。

## 适用环境

在 macOS 上用 Claude Code 和 Codex 跑出来的，素材以中文会议录屏、课程和辅导录屏、讲座录音为主。文中的数字都是那些素材上的实测，换了素材要重测，不要照抄。

换到别的系统，这几步要自己验证：

- 源文件进回收站：`scripts/trash_source.py` 用 Finder 删除，只在 macOS 上能跑。
- 硬件编码：`hevc_videotoolbox` 是苹果的编码器，其他平台换成各自的硬件编码器，参数要重测。
- 出 PDF：`scripts/md2pdf.py` 里写死了 macOS 上 Chrome 的路径，版式用的是苹方字体。

文中标着「默认做法」的地方是一种选择，后面写了理由，理由对你不成立就按你的习惯改。其余的是踩过坑之后的约束，改之前先读懂那次失败。

## 先试 FluentFlow Local 的 MCP，脚本是降级路

FluentFlow Local 是一个开源的本机转写应用：https://github.com/Userneima/fluentflow-local 。
没装的先按它 README 的「安装」装好，再按「让 Claude Code、Codex 等 AI 工具调用它」一节把 MCP 注册到当前宿主。
不装也能用本 skill，只是只剩下面的脚本降级路。

这六件事在 FluentFlow Local 里是产品功能，不是一堆待拼的脚本。**默认走 MCP**：
`mcp__fluentflow-local__submit_local_media` 收一个本机绝对路径，`debreath_task`、
`write_note_from_cut_media` 接着走完剪辑和笔记。产品路能用云转写和自动写笔记，脚本路这两样都没有。

**产品路要求当前宿主注册了 `fluentflow-local` 这个 MCP server，这是宿主各自的配置，不随本
skill 一起分发。**先看自己的工具里有没有 `mcp__fluentflow-local__*`：没有就直接走脚本降级路，
或者先去补这个宿主的 MCP 注册，别把「后端在 8000 上活着」当成「我能用产品路」——2026-09-17
在 Codex 上实测过这个组合：`127.0.0.1:8000/health` 正常，但那边没有这个 MCP 条目，工具不存在。

### 开工前先确认在跑的是哪个版本

提交之前先看一眼，比拿到报错再回头查省事：

```bash
curl -s http://127.0.0.1:8000/health
```

要看到 `"edition":"local"`。后端自己声明身份，**判据是这个字段，不是「8000 上有东西应答」**。
同一份回应里的 `accepted_agent_inputs` 会列出它收哪些输入。

- 没有应答：打开 FluentFlow Local 应用，等它把浏览器打开再回来。
- 有应答但 `edition` 不是 `local`：8000 上跑的是别的程序，先退掉它，再起 FluentFlow Local。
- 起来了但提交返回 401/403：本地 Agent API 要靠 `fluentflow-local` 仓库根目录的 `.env` 里那条
  `FLUENTFLOW_ACCESS_TOKEN` 打开，值要和当前宿主 MCP 配置里 `fluentflow-local` 条目的一致（Claude Code 在 `~/.claude.json`）。

**后端拒绝时先确认版本，不要改它的源码或切它的分支来迁就工具。**判成「MCP 工具领先于后端版本」然后放弃整条产品路，
代价是丢掉云转写和自动笔记，英文术语只能人对着画面补。

### 什么时候才降到脚本

后端确实起不来时（依赖缺失、端口被别的程序占着、readiness 检查不过），`fluentflow-local` 仓库里的 `scripts/debreath_batch.py`
直接调同一个剪辑引擎，只要 ffmpeg。**代价要在动手前说出来**：转写掉回本地 whisper（见下面「本地模型对现场
中英混杂录音有明确天花板」），笔记得自己写。

自动写笔记那一步还要本机 Claude 处于登录状态，过期时后端会记 `automatic note failed`，任务其余部分照常完成。

## 第一步永远是看素材，然后才定参数

**这一步不能跳，也不能用上一份素材的参数代替。**

抽三到五帧，**读画面里最小的字**。然后按看到的东西分路：

| 画面里有什么 | 分辨率怎么处理 |
|---|---|
| 需要读的细节：白板、代码、正文、表格、幻灯片、密集小字 | **保持原分辨率** |
| 人脸、大字标题、静态背景、纯音频 | 可以降到一半宽度 |

### 为什么这一步必须做

因为**同样规格的两份素材，正确参数完全不同**。

一次真实的失败：两份录屏，同样是 2940×1718、60fps、6 Mbps，来自同一台设备。第一份画面主体是人脸和聊天窗口，宽度减半后看不出差别，体积降到十分之一。**第二份是白板上满屏的小字，同样减半之后文字糊到「费劲能读」**，素材的主要价值当场损失。

**参数错了不会报错**——渲染自检全部通过，时长、音画同步、帧数都对，只有人眼能看出来。

### 两个反面做法

**不要把判断推给用户。** 「我先给你看对比图，你决定降不降」听起来谨慎，实际上是把工作推回去——**在你跑完之前，用户手上没有任何东西可判断**，他的意见只可能出现在下一轮。看素材、定路径是你的工作。

**不要用整帧平均的指标代替看画面。** 曾经试过「降一半再放大回来算 PSNR」这个看似客观的判据，结果**两类素材测出来几乎一样**（25.9–28.3 dB 对 26.4–29.8 dB），完全分不开。原因很简单：白板九成面积是空白背景，降分辨率对空白毫无损失，**整帧平均把真正出问题的那一小块文字区域洗掉了**。同类的判据（边缘对比度之类）能分开「人脸 vs 屏幕」，但分不开「大字的屏幕 vs 密集小字的屏幕」——而后者才是这里的分界。

**要判断画面能不能降，就去看画面。这件事没有替代品。**

## 剪空白（去气口）

原理是探测声学静音再剪掉，**不判断内容**——它不知道哪句是废话，只知道哪里没人说话。判断废话需要理解内容，是另一个量级的成本。

### 阈值不要手填，让它按材料自己量

「多轻算静音」这条线取决于材料本身。一个正确的实现会在剪之前量两个值：

- **气口电平**：短窗口响度分布的低端，也就是间隙实际有多安静
- **说话声电平**：同一分布的高端

**阈值必须落在这两者之间**——够得着气口，又不碰说话声。

### 三种失败形态，都不报错

**一、剪出 0.0% 却报告成功。** 阈值够不着这份材料的气口。

最常见的原因是**音频做过降噪或音量「增强」**：那类处理会把说话之间的间隙一起抬起来，整体音量看着完全正常，气口却被填平了。实测同一场讲座的两个版本——原始录音的气口在 -45.1 dB，增强版被抬到 -35.3 dB，**两者整体音量都在 -20 dB 左右，从整体音量完全看不出这个差别**。默认阈值下，原始版找到 771 处气口剪掉 11.6%，增强版找到 6 处剪掉 0.0%。

**所以：手上有原始版和增强版时，剪气口一定用原始版。** 顺带一提，增强版对转写质量也没有帮助（实测两者一样差），所以那道处理的价值只在人耳听感，不该当作处理流水线的输入。

**二、阈值被调得过低，同样剪不出来。** 如果实现里有「材料太轻就下调阈值」这类逻辑，注意它的判据：**用整体平均音量代替说话声电平是错的**，因为平均值会被静音比例拉低——一场有 11.6% 空白的讲座平均只有 -29.1 dB，而它的说话声在 -25 dB，完全正常。按平均值判断会把它误判成「录得太轻」，阈值下调到 -44 dB，**771 处气口变成 1 处**。

**三、切进人声。** 说话声本身很轻（低于或贴近阈值）时会发生。

### 有些素材真的剪不动，这不是流程出错

当**气口和说话声相差不到 18 dB** 时，中间放不下一条干净的线。实测五份会场录音：说话声在 -29 到 -32 dB，气口只低 7.5 到 16.4 dB——**任何阈值都剪不出超过 0.2%**，取两者中点也一样。原因是会场离讲者远、底噪连续，真正的静音段几乎不存在。

这种情况**正确的行为是保护说话声、如实报告剪不了**，而不是硬选一个数字装作能剪。硬剪的代价是切进人声，比剪不动更糟。

### 剪出来的量小到没意义时，不要渲染

剪掉不到 0.5% 还去重编码，等于花一次有损编码换一个和原片一样长的文件。实测两份素材找到 1 处和 10 处气口、剪掉 0.0%，仍然被渲染了一遍（57.9MB 进、57.5MB 出）。

## 默认做法：剪完就把源文件送进回收站

剪后文件一旦通过核验，下游全部绑在它身上——转录稿的时间点、字幕、笔记引用的都是它。
源文件此时只是几倍体积的重量（一份 16 分钟会议录屏：源 767MB，剪后 105MB）。所以剪完就送走，
不用等笔记和 PDF。

```bash
python3 scripts/trash_source.py <素材/源文件> <剪后文件> <过程文件/剪辑表.json>
```

**送进回收站，不是删掉。** 第一步那个分辨率判断是这条流程里唯一没有自动判据的环节，只有
人眼能发现「白板小字糊了」，而重渲染画面要读源文件。回收站把这条退路留着，代价是不立刻
腾出硬盘——真要腾就自己倒一次。

脚本自己核六件事，任何一件不过就原样留着源文件并说出理由：剪后文件带着 FluentFlow 的
剪辑标记；音轨在、源片有画面则剪后也有画面；源文件时长对得上剪辑表记的源时长（确认这三个
文件是一组的）；剪后时长对得上剪辑表算的保留时长（截断的渲染会在这里现形）；剪辑表的抽查
判定气口和说话声分得开；剪辑表没带警告。

**剪不动的素材不走这一步。** 剪辑表带警告、抽查说贴着人声、剪出来的量小到没渲染——这三种
情况下源文件就是将被观看的那个文件，它是成品，不是过程。脚本会拒绝，这时候该做的是看警告，
不是绕过检查。

**但「剪不动」不等于「不能压」，而这条岔路脚本盖不到。** 剪不动的大体积录屏仍然该重新编码
（见下面那节），压完之后成品是那个压缩版，源文件同样该进回收站——可脚本只认剪气口的产出
（要有 FluentFlow 的剪辑标记和配套剪辑表），对一个纯重编码的文件会直接拒绝。**这时候要自己
补这一步**，别因为脚本没管就把 2.5GB 的源片留在那儿。自己核这四项，全过才动：时长一致、
分辨率没降、音轨在、源片有画面则产物也有；再加一条脚本没有的——**把产物完整解码一遍看退出码**。

**Finder 的自动化权限被拒时会掉到手动移动。** 那种情况下脚本改成自己把文件挪进
`~/.Trash`，一样能恢复，只是 Finder 里没有「放回原处」，得手动拖。要那个功能就在
系统设置 → 隐私与安全性 → 自动化里给终端勾上 Finder。

## 体积：大头在码率和分辨率，不在时长

剪掉 30% 的空白只省 30%。真正决定体积的是码率和分辨率。

### 码率必须按源码率封顶

**用固定画质档编码会让低码率素材不降反增。** 实测一份 1920×1080 的会议录像，源码率只有 752 kbps，用固定 crf 20 编出 957 kbps——**剪掉了 13.6% 的时长，文件反而变大了**。

原因：固定画质档假设源片是「正常码率」。已经压得很省的素材（会议录像、录屏常见 0.1–1 Mbps），再按那个档位编码就是为原片里根本不存在的细节买单。

**做法**：编码前量一次源片码率，拿它当上限（`-maxrate` 之类），画质目标不变。宽裕的素材碰不到上限、结果和以前一样；压得狠的素材不再多花比特。音频同理——源片只有 64 kbps 时不该写成 128 kbps。

### 分辨率见第一步

**这一项没有任何测量能替你决定，所以默认不降。** 要降就先看画面。

### 编码器和参数按源码率分路，不要抄一组固定命令

**这一节有两组实测，方向相反。先看你手上这份源片的码率，再决定抄哪一组。**

共同的一条：**硬件编码必须自己指定关键帧间隔，按「5 秒 × 帧率」给。**VideoToolbox 默认大约每 12 帧插一个（60fps 素材上是 0.2 秒一个），而屏幕录制的源片通常是 5 秒一个。关键帧是整幅重新编码，极贵。

两组实测，**同一个缺陷在不同码率档上表现成两种完全不同的症状**：

| 源片 | 默认 | 指定 `-g` 之后 |
|---|---|---|
| 2940×1718、6 Mbps | 50 个关键帧 / 600 帧，23MB | 1 个，**5MB**，文字无差别 |
| 1920×1080、517 kbps | 291 个关键帧，3.36MB，**文字在 3 倍放大下完全不可读** | 12 个，2.16MB，和源片一样清楚 |

高码率那档有余量可以浪费，所以只看得见体积变大；低码率那档没有余量，浪费掉的比特直接从文字上扣。**所以不要把这一条理解成「省体积的优化」，在低码率素材上它是能不能读的问题。**

上面两组都是屏幕录制，画面大面积静止。**真人实拍上方向一样但量级差得远**：一份 640×360 / 25fps / 266 kbps 的访谈小 8%，一份 1024×576 / 30fps / 1709 kbps 的快剪解说小 3.5%，对比录屏那档的 37%。画质上两边都没有代价（脸部放大 5 倍，有无 `-g` 分不出来）。这两组实拍各只测过一份，不要据此说「实拍上已广泛验证」。

所以：**这个参数任何素材都该给，但指望它把文件砍小的只有屏幕录制。**

下游有东西按这个信号做判断：视觉笔记那条链路用 `-skip_frame nokey` 在剪后文件上找画面变化，关键帧间隔就是它能取到的最细粒度。5 秒和 libx264 的默认值在同一量级，所以软硬两条路径对同一个文件给出的密度是一致的。**要是把 `-g` 放到远大于 5 秒，先去看这条链路。**

**源片码率高（实测 6 Mbps，2940×1718）：硬件 HEVC 加恒定质量，又快又小。**

```bash
ffmpeg -i in.mov -c:v hevc_videotoolbox -tag:v hvc1 -q:v 50 \
  -spatial_aq 1 -prio_speed 0 -g 600 -pix_fmt yuv420p \
  -c:a copy -movflags +faststart out.mp4
```

同负载下对比 x264 crf20（同样 `-g 600`）：硬件 35 秒 / 5MB，x264 89 秒 / 8MB，文字在 3.2 倍放大下都和源片一样。

**源片码率中等（实测 1900 kbps，2560×1600）：反过来，x264 按源码率封顶最好。**

| | 耗时 | 体积 | 文字 |
|---|---|---|---|
| x264 crf20，`-maxrate` 封在源码率 | 17 秒 | 10MB | 和源片一样 |
| 硬件 HEVC，`-q:v 50` | 27 秒 | 6MB | **糊了** |
| 硬件 HEVC，`-b:v` 给到源码率 | 27 秒 | 13MB | 和源片一样 |

同一个 `-q:v 50`，在 6 Mbps 素材上扛得住，在 1900 kbps 素材上就压过头。画幅小一些的时候 x264 还更快。

**所以判据是源片码率，不是「这是不是屏幕录制」。**低码率的素材本来就没有细节可留，恒定质量模式会替它编造，编造出来的就是糊。`fluentflow-local` 仓库里 `encode_args_for_source` 那条「按源片自己的码率封顶」的规则在这一档是对的，直接用默认路径即可。

**拿不准就在这份素材上跑一次 60 秒的对比**，抽同一时刻的帧裁到文字区域放大三倍看。不要用整帧平均指标，屏幕录制大面积是空白，会把结果洗掉。

**一次测量只覆盖它测过的那个码率档。**「屏幕录制一律用硬件 HEVC 加 `-q:v 50`」在 6 Mbps 素材上成立，搬到一批 1900 kbps 的辅导录屏上就把字压糊了，那一档该用的是按源码率封顶。

**结束时那行 `Error encoding frame: -12912` 不一定是失败。**同一次运行里，ffmpeg 自己的最终统计（`Lsize=` 那行）已经写到完整时长和完整帧数，报错是写完最后一帧之后收尾时抛的。判断成没成要**完整解码一遍产物**看退出码，不要看最后一行长什么样。

## 转写

### 本地模型对现场中英混杂录音有明确天花板

实测一场技术讲座（会场扩音、中文夹英文术语）：中等档和更大档的本地模型**把同一批词认错**，专业术语和英文词持续出错，给术语提示词也救不回来，某些词反而更差。

**所以不要指望换更大的模型解决这件事。** 换模型之前先接受：转录稿会有错，而**下一步（写笔记）才是消化这些错的地方**——写笔记的模型能从上下文认出「架构湿润」是「架构设计」，而转录稿本身没有这个能力。

### 转写剪后的文件，不要转原片再映射

字幕的时间点必须属于**将被观看的那个文件**。转原片再把时间轴映射到剪后文件，是笔记描述一个文件、时间点却属于另一个文件的经典来源。

如果确实只有原片的字幕（比如素材自带），那就按剪辑表重算时间轴，并记录重算丢了多少条、缩短了多少条。

### 剪不动的素材也要有转录稿

「没剪出东西」不等于「不用转写」——**剪不动时，原片就是将被观看的那个文件**，转录稿属于它。跳过这一步会让最需要转录稿的那些素材恰好没有。

## 写笔记

### 画面和照片是纯录音拿不到的部分

如果素材是**录屏**，或者现场有**幻灯片照片**，那么配置项、清单、代码、表格这类原文**从画面抄，比从转录稿抄可靠得多**。

一次实测：一场讲座的转录稿把工具名认成了五种不同的错误拼写，而幻灯片照片上是清清楚楚的原文。凡是「屏幕上写着但讲者没读出来」的内容，转录稿里永久不存在。

### 不要重复已有的成品

如果素材配了正式文档（PDF、白板、讲义），**笔记的价值不在复述它们**，而在记录口头讲的方法、判断和现场问答——那些是文档里没有的。笔记开头指向那些文档即可。

### 只标出你猜的那部分，不要列还原对照表

转录稿有错，笔记里必然要还原。但还原分两类，**只有一类需要告诉读者**。

纯粹的语音识别错字——「谋差」是「摩擦」、「环占」是「ERP」——改掉就完了。这类没有任何理解风险，没人会去核，列出来只是把过程摊开给读者看。

真正要留痕的是**你猜的那部分**：人名、机构名、产品名、对不上的数字。这些写进「存疑」那节，说清楚转录稿不可读、你没有填，或者你填了什么、依据是什么。

**不要在笔记末尾列「转录稿里是什么 → 还原成什么」的对照表。**那张表会把两类混在一起，占掉整整一页，而其中绝大多数行是错字。它记录的是处理过程，该留在对话里，不该进交付物。

同理，**「录音里混着旁边的杂音」「这段音质差」「我用的是哪个模型」这类关于素材和工艺的说明也不进笔记**——笔记里本来就没有杂音，读者遇不到这个问题。素材有问题就在对话里说一句。

### 有冲突的数字拒绝采信

版本号、百分比、机构名、人名——转录稿里出现互相冲突的说法时，**不要挑一个写进正文**。写明「有冲突，请回听确认」。

一次实测：同一场讲座的转录稿里出现了三个互相矛盾的版本号。挑一个填上去，比留空更危险——它会被当成事实引用。

## 笔记同时出一份 PDF

**默认做法：笔记写完就出 PDF，不用等人开口要。** Markdown 是给下一轮加工用的，PDF 才是能直接发出去、能打印、能在上面写字的那份。

用 `scripts/md2pdf.py`（Markdown → 打印版 HTML → Chrome headless 出 PDF）：

```bash
python3 scripts/md2pdf.py <笔记.md> <同名.pdf>
```

它只依赖 Chrome 和 Python 的 `markdown` 包（`pip install markdown`），不需要 pandoc 或 LaTeX——中文在这两条路上都要额外配字体，而 Chrome 直接就有系统里的苹方。

### 出完必须自己翻一遍

**这不是可选的检查。** 一次真实的失败：一份笔记里嵌在列表下的五个步骤，在第一版 PDF 里被压成了一整段流水句——**源文件用两个空格缩进，而 Python-Markdown 要四个**，浅了的缩进会被当成上一行的续写。脚本里已经做了缩进加倍来兜住这件事，但同类问题（表格塌了、引用块吞掉后面的段落）只有翻页才能看见。

**渲染不会报错**，PDF 一样生成、页数一样正常。

### 默认版式

`md2pdf.py` 按下面这套出，要换版式直接改脚本里的 CSS：


- **A4，正文 10.5pt / 行高 1.78**，中文标点用 inter-ideograph 对齐
- **引用块做成浅色卡片**——这类笔记的关键句大量用 `>`，做成卡片才扫得到
- **表格、引用块、标题都设了不许跨页断开**
- **不加页码**。Chrome 的页眉页脚会把本地文件路径印在页脚上，很丑；CSS 的页码计数器 Chrome 又不支持。

## 产物：剪辑表是主产物，视频是它的一次渲染

**剪辑表**（剪在哪、用了什么阈值、为什么用这个阈值）必须存下来。理由很实在：

- **换参数重渲染不需要重新分析**，也不需要重新转写
- 从一个成品视频里**恢复不出**这些决定

一次实测的收益：发现分辨率定错之后，靠剪辑表只重渲染了画面，**省掉了重新分析和重新转写的十几分钟**——而字幕和转录稿完全不用动，因为它们绑定剪辑表，跟分辨率无关。

**默认做法：产物折叠成一个文件夹**，一个素材一组：

```
<素材名>/
├── <素材名>_笔记.pdf     ← 成品
├── <素材名>_去气口.mp4   ← 成品：源文件进回收站之后，这是唯一能看的那一份
├── 素材/                  ← 现场照片、幻灯片、讲义这类不是过程的输入
└── 过程文件/              ← 笔记 md、字幕、转录稿、剪辑表、词级时间戳、音频、抽出来的帧
```

**分界线是「人会不会打开它」，不是「它是不是最终产物」。** 外面只放 PDF 笔记和剪后视频，
这两样是人真会双击的。Markdown 笔记和字幕虽然也是产出，但人不看 md、不看 srt，它们的用处
是给下一轮处理和重新排版，所以跟转录稿、剪辑表一起收进 `过程文件/`。

剪后视频尤其不能埋进 `过程文件/`：源文件核验通过就进了回收站，它是这场录像唯一能播的版本。
产品渲染出来的名字是 `<素材名>_debreath.mp4`。交付时的后缀是个人习惯，这里默认改成 `_去气口.mp4`，
跟 `_笔记.pdf` 一样用中文，换成你习惯的命名即可。

**为什么默认就折叠，而不是等文件多了再收**：一个源文件会摊出六个附属文件（剪后媒体、字幕、纯文本、词级时间戳、剪辑表、笔记），**第二个素材进来就是十四个**，主目录很快就认不出哪个是能直接用的成品。用户看到一屏文件名的第一反应是「怎么这么多」，而不是「产物很齐全」。

**源录音不在这个文件夹里**，它在剪完通过核验之后就进了回收站（见上面那节）。处理期间先把它
放进 `素材/`：下次批量处理会照文件夹扫，散在外面容易连着产物再扫一遍。剪不动的素材是例外——
那时源文件就是成品媒体，留在 `素材/`。

源片一进回收站，`素材/` 通常就空了。**收尾时空的 `素材/` 直接删掉**：一个空文件夹不告诉读者
任何事，却要人点进去才知道里面没东西。批量处理十几场就是十几个。

**外面只留人会打开的**：PDF 笔记、剪后视频，以及本来就存在的成品附件（比如素材配套的讲义）。

**笔记里不要嵌视频抽帧。** 录屏抽出来的帧是整块桌面：浏览器标签、程序坞、侧边栏全在里面，
真正的内容只占中间一块，还经常被窗口边缘切掉。再经过一次重编码，正文小字已经糊到读不出来。
一份十页的笔记塞十几张这样的图，体积涨三到四倍，读者什么也没多知道。2560×1440 的录屏也一样：
大标题勉强能认，正文小字不行。
帧仍然要抽——写笔记的模型靠它们看懂白板和幻灯片上的内容，把内容**写成文字**；抽完的帧收进
`过程文件/截图/`，不进正文。

## 批量处理时的三个守卫

这三条都来自真实的批量失败：

**一、跳过自己的产出。** 产物按输入命名时，第二次运行会把上一次的产物当成新素材。一次失败：15 个文件被剪和转写了两遍，产生 246MB 重复文件。**检查文件里的处理标记**（比检查文件名可靠——名字会被改、文件会被移动），文件名后缀也一起查。

**二、自己遍历路径，不要交给 shell 展开。** 文件名带空格是常态，shell 拆词之后一整批素材会「什么都没量」，而且它**不报错**，只是安静地跳过。

**三、剪出 0.0% 要在结果里显眼地说出来。** 一次失败：十个文件里四个剪出 0.0%，每个都报告「ok」，于是「这批没气口可剪」这个错误结论被接受了——而真相是阈值离材料差了 10 dB。**逐个文件说一次，汇总时再说一次。**

## 这份 skill 覆盖不了的

- **判断哪段是废话**：需要理解内容，成本比机械剪空白高一个数量级。剪空白只处理「没人说话」。
- **剪辑创作**：转场、配乐、调色、逐帧标注。
- **画面里那些字的语义**：如果需要笔记引用屏幕上的内容，得让能看图的模型真的看画面，而不是从转录稿猜。
