# 长文优化

用户已经写完一篇长文，要把它改到能发出去。你的任务不是重写，是**找出问题、按严重程度排序、逐层落地**。

## 适用范围

从改技术科普和产品解读长文里总结出来的，发布渠道主要是微信公众号，稿子放在飞书文档里协作。换了渠道，第 2 层的开篇规则和第 6 层的排版要按那个渠道重新判断；其余几层跟渠道无关。

标着「默认做法」的地方是一种选择，后面写了理由，理由对你不成立就改。

## 顺序不能打乱

1. **事实** —— 先核。事实错了，后面所有句子都是白改。
2. **结构** —— 砍重复章节。先抠句子再砍章节，抠掉的那些句子会跟着章节一起没。
3. **语感** —— 逐句去 AI 味。
4. **自家产品段** —— 单独过一遍（见第 4.5 层）。这一段的失真方式和别处不一样。
5. **硬伤** —— 统一扫一遍标点和空格。
6. **排版** —— 最后做。内容还在增删时做排版，等于白做。

**默认做法：一次只做一层，做完汇报**，等用户认可再做下一层。一口气全改完再说，用户没法判断哪一步跑偏了。用户明确说「直接全改完」时照做。

## 第 1 层：事实

**文章讲某个开源项目或产品，就必须去它的仓库/官方文档核，不能只靠文章内部自洽。** 本地有 clone 就 grep，没有就搜官方 repo 和 docs。

重点核这几类：

- **命名**：模式名、版本名、组件名。文章里的叫法常常是作者从二手文章里抄来的，官方根本没这个词。
- **能力清单**：文中说「它把 A、B、C 都做成了插件」，逐项到 `packages/` 或文档里对。
- **数字**：能自己算的当场算；引用别人的必须追到一手来源，追不到就换成不会错的说法（「上千条记录」而不是精确数字），并告诉用户你只核到二手。

> 真实教训：一篇讲 DeepSeek Harness 的文章，第五章列了「标准模式、PTC 模式、极简模式、创造模式」，第六章又单独讲 Code Mode。查仓库 `apps/cli/config/agent-presets/` 只有 `standard`、`code`、`minimal`、`cordis` 四个，`code` 那份配置注释第一行写着 "presented as Code Mode"——PTC 和 Code Mode 是同一个东西，而且全仓库搜不到 "PTC"。光读文章永远发现不了，而这个错误正好解释了读者觉得那两章别扭的原因。

**核验方法本身要先用已知样本验证。** 查外部引用时，先拿一个你确定存在的样本跑一遍同样的查法，确认这条路是通的，再去查待核的那些。

> 真实教训（2026-08）：核两条 arXiv 引用，直接 `curl` 拿到 200 就说"链接没问题"——而 `arxiv.org/pdf/任意字符串` 都返回 200，这个结论方法上就是错的。改用 arXiv API 后又全部"查无此文"，差点当成"引用是编的"报出去；先拿一篇确定存在的论文做对照，才发现是 http 走不通、换 https 三条全命中。**引用是真的，我的方法是坏的。** 没有对照组，两次都会得出错误结论——一次放过真问题，一次制造假问题。

还有一类更隐蔽，因为它伪装成文风问题：**为了让故事好听而把事实说糙**。

判据是一句话同时做到两件事——让叙事更有戏剧性，让事实更不准。典型例子：写「每次留下来没人管的，也是同一类东西」，比「排在后面、还没轮到」带劲得多，但它把顺序问题写成了疏忽，读者会以为整个行业一直在犯迷糊。这类句子光读稿子发现不了，因为它在文章内部完全自洽；只有懂这一行的人看到才会说「不对吧」。**发现后改回准确的说法，哪怕它没那么有劲。**

还有一类要处理：**空引用**。「业界普遍认为」「经典教科书对它的定义大同小异」——没有出处的权威口吻是 AI 写作最明显的指纹。要么补出具体出处（哪本书、哪个人、哪篇博客），要么整句删掉。

## 第 2 层：结构

先跑量化，比通读可靠：

- **核心结论或公式在正文出现几次？** 超过三次基本就是重复。
- **有没有两章在回答同一个问题？** 把每章标题和首段列出来，看功能是否重叠。典型症状是读到后面觉得「这个我刚才看过」。
- **有没有一章问了两个设问？** 一章只该问一个问题。开头问 A、中间突然转成 B，读者不知道这章在讲什么。

常见处理：

- 后面那章在重写前面那章 → 砍掉后面的八成，只留收束和图，与下一章合并成一章。
- 过渡段自问自答两次 → 删掉第二次那句设问，让内容直接接上。
- 同一个公式反复亮相 → 只在首次出现和最终收束处保留。

还有一条是开篇的：

- **第一屏不要罗列技术概念。** 面向公众号这类渠道，开头就辨析术语会直接流失读者。先给一个日常场景，让读者在自己的经验里认出这个问题，再引到技术上。例：讲 context 之前，先写同事甩来一句「这个方案我看了」——他上一句是「昨晚熬到三点」还是「今天会太多」，同样七个字理解完全相反；然后才说模型没有这些背景、全靠当场喂。**判据：第一屏有没有一句话是读者不用懂技术就能点头的。**（来源：2026-08 公众号渠道的评审意见，原话是开头一定不要罗列一堆技术概念，那样很容易让读者流失。）

## 第 3 层：语感

句子层面的写作取向见 `natural-chinese-writing`，不在这里重复。这一层只讲**长文里怎么把它们找出来**。

三个可以数出来的信号，跑一遍计数比通读有效：

- **「所以 / 其实 / 真正 / 这也是为什么 / 值得注意的是」出现次数。** 一万字里「所以」出现二十次，意味着几乎每段都在给上一段下结论——这是模型的习惯，不是人的。砍一半，让句子直接往下接。
- **冒号当停顿用。** 判据：冒号后面既不是列举也不是定义，只是把一句话掰成两半制造节奏。例：「它既是行动系统，也是一台：Context 生产机器。」这是短视频文案的写法，密度一高就假。
- **翻译腔长定语。** 判据：一个名词前面挂了二十字以上的修饰。例：「模型被放进一个能够不断与环境交互的闭环之后形成的系统」。中文不这么说，拆成两句。

再加三条今天实测有效的：

- **抽象修饰词是"我没去看原始材料"的信号。** 写出"不是线性的、也不是均匀的""整条链路第一次浮上水面"这类句子时，基本可以断定自己在转述别人的结论标签，而不是在讲具体内容。处理办法不是换个词，是回去把具体的东西找出来——那份报告到底测出了什么、多出来的活具体是哪几件。**读者读到抽象词会产生好奇，而你没打算解答，这是最伤的。**
- **同一句式在每节重复出现 = 模板感。** 一个贯穿全文的结构标记（每节结尾都开启下一个问题）是好的，但**措辞必须每节不同**。连着五节都写"它留下的坑是"，读者感受到的不是结构，是填空。
- **主语含糊会让读者代入错的那个。** "从你自己的资料里找出最相关的几段"——谁找？读者默认代入自己，于是把 RAG 理解成"我准备一段背景提示词"，而全文主线恰恰是"决定权从人转给了程序"。**凡是关键动作，明确写出是谁在做。**

再加四条（2026-08-19 实测，全部来自读者逐句标注）：

- **贯穿全文的抽象接缝词，和重复句式一样是模板。** 上一条说的是句式，这条说的是词：为了让各节对齐，造一个抽象名词，每节点一次——「乐观就出现在这儿」「乐观也从这里来」「这次的乐观是」。措辞每节都不一样，照样被一眼认出来，因为那个词本身是空的。**判据：这个词是文章里真实存在的东西，还是我为了接缝造出来的？** 读者的反应会是「这句话啥意思」。
- **替读者归纳的引导语。** 「这一轮留下来的东西是」「这一轮真正的观念变化是」「这个认识后来没被推翻过」。共同点是先宣布「我要给你总结了」，再给一句抽象的话。改法是删掉引导语、直接说具体的事：不写「输入第一次有了独立地位」，写「以前想让模型干件新事得拿数据重新训一遍，现在把例子写进输入里就行」。
- **对引用材料下评价。** 「某某写得很干脆」「还有一笔更朴素的账」。读者要的是材料说了什么，不是你给它打的分。直接引，别点评。
- **给后文埋的伏笔。** 「这个毛病后面还会再犯一次」是讲义腔。真有呼应关系，只在后文回指一次就够，不要在前面预告。

还有一条数不出来但最要紧：

- **通篇有没有一个「人」。** 如果所有「我们」「你」都是泛指、所有判断都没有来处，读者会默认这是查资料总结出来的——而那正是 AI 味的根。最好的解法是补一件真发生过的事，形状是「我们本来以为 ___，结果 ___，后来改成 ___」。**作者自己给不出案例时，退而用有出处的公开案例**（真实事件 + 可点开的链接），效果次一等，但仍远好过空口结论。绝不允许编造经历来填这个空。

### 收尾：说完就停

**结尾想要一句「收得住的话」，这个念头本身就是长文里 AI 味最大的来源。** 典型形状是三样同时出现：先免责（「这是判断，不是已经被验证的事」），紧接着拔高（一句对仗工整的金句），还加粗。免责在这里不是谦虚，是给后面那句大话开路。

**实测教训（2026-08-19）**：一句被指为 AI 味的收尾，重写一遍往往还是 AI 味——第一次把金句换成了「稍微朴素一点的金句」，照样被读者指出来。**正确动作通常是整段删掉**，让文章停在前一段的具体内容上。

判据只有一个：**这段有没有新信息？** 只是把前面说过的话用更响的方式再说一遍，就删。同理，「如果只记三句话」「总结来说」这类编号收尾，在长文里一律不要——正文说清楚了就不需要，没说清楚也补不回来。

## 第 4 层：术语括注

- 括号**紧跟名词**，里面只放一句大白话：`Preset（提前组合好的一套模型、工具、插件、权限和运行方式）`。
- 不写 `X（即 Y：解释）` 这种壳，也不在括号里把那个词重复一遍。
- 只在**第一次出现**的地方解释。解释散落在后文的，往前挪，后面那份删掉。
- 独立成段的解释收回名词后面，不要让一句括注自己占一整段。
- **产品或项目的内部命名不解释**。Code Mode、PTC 这类只是某个产品给自己模式起的名字，不是通用概念，硬加一句「即代码模式」反而像在定义一个不存在的东西。
- 不要自己判断哪个词「够基础可以不解释」——这是因人而异的。拿不准就解释。豁免只认作者明确说过不用解释的词。
- **这一层要跑一个清单，不能靠边读边想。** 把全文的英文缩写、产品名、技术名词、许可证名、版本号全部列出来，逐个问「第一次出现时解释了吗」。**你熟的词最容易漏**——因为你不会在它面前卡住。（真实教训：一篇稿子里 embedding、chunk size、Apache-2.0、RRF、Leiden 都是这么漏掉的，全靠读者逐个指出来。）
- **解释要答"作用是什么"，不只是"中文叫什么"。** 把 embedding 注成"向量"是同义词替换，不是解释；读者的问题是"算这串数字有什么用"。同理 RAG 注成"检索增强生成"等于没注——得说清它解决的是"模型不知道你公司的事"。

## 第 4.5 层：写到自己参与的产品时，单独过一遍

这一层是独立的，因为**同一个人写别人的产品会很具体，写自家产品会自动切换成"介绍口吻"**。今天一篇稿子里，讲别家产品那节画面清楚，讲自家产品那段全是抽象名词互相解释——不是能力问题，是位置问题。

五个症状，出现任意一个就重写那一段：

1. **抽象名词互相解释，给不出画面。** "把查询本身变成 Agent 能调用的东西""拿到的是一个边界清楚的入口"——读者看完不知道那东西长什么样。**判据：这段能不能想象出一个具体画面？** 想不出就是在写介绍，不是在说事。改法是给一个具体场景（要查什么、以前怎么做、出什么问题、现在怎么做），落到一个能想象的东西上——例如"Agent 看到的不是数据库，是一个只能填两个空的工具"。
2. **对仗和排比。** "不是搬走数据，而是……""数据留在原处，权限留在原处"。整齐的句式在产品文案里是加分项，在文章里是 AI 指纹。
3. **自造的抽象名词。** 层、入口、落点、有地方落、统一的落点。自家产品最容易催生这类词，因为你脑子里有架构图，而读者没有。
4. **伪装中立。** "它把自己定位成……"——如果这是自家渠道，读者知道你是谁，第三人称只会两头不落好：既没有旁观者的可信度，又让本该坦诚的话显得像打太极。**挑明立场反而给坦诚挣来可信度**："我们做的就是这一端"。
5. **一堆免责声明。** 免责是推介的伴生物：读者没被推销任何东西时，没有什么需要打折扣。**如果你发现要写两段来解释"哪些还没做到"，先回头看前面是不是吹过了。** 去掉推介，免责自然就不需要了。

还有两条是范围判断，比措辞更要紧：

- **产品定义没在内部敲定之前，对外只写方向、不写功能。** 功能清单会过期，也会逼你补一串"这条还在推进中"。方向不会。这一条同时解决了"哪些能写哪些不能写"的全部纠结——**只讲今天成立的事，就自动守住了"不把规划写成现状"这条线**。
- **介绍要接着上文刚提出的问题往下答，不要另起一段罗列。** 上文说这一层要解决两件事，那就说我们怎么对上这两件——这样它读起来是论证的收尾，而不是插播广告。判据很简单：**把这段删掉，上文的问题是不是就没人回答了？** 是，它就该在；不是，它就是硬塞的。

## 第 5 层：硬伤

统一扫一遍：中英文之间的空格、全半角括号混用、缺句号、箭头前后空格不一致、半角连字符 `--` 当破折号用、中文引号混用（`「」` 和 `“”` 不要同时出现）、标题里的日期或编号发不发出去要问作者（那可能是他的归档习惯，别自作主张删）。

## 第 6 层：段落排版

**首行缩进和段间空行，中文长文里二选一，绝不能同时用。** 两个都上会显得乱。选哪个是默认做法：面向网页、公众号这类屏幕阅读选空行，排版成书或 PDF 才用缩进。

哪里该空一行：

- 段与段之间。
- 列表结束之后，下一段开始之前。
- 引用块、代码块结束之后。

哪里**不**空：

- 引用块或代码块，和它上面那句引入句之间。「文档里举的例子是：」跟那段引文是一句话，贴着才对，中间空一行会把它们拆成两件事。
- 列表各项之间。
- 标题前后——编辑器自带间距，手动再加就过宽了。

**这一层必须放在最后。** 空行是插进正文里的空块，一旦后面又增删段落，空行就会错位：删掉一段而没删它后面那个空块，就留下连着两个空行；插入新段落而忘了带空行，那一处又贴死。改完内容再一次性铺，比来回补要省事得多。

## 落地到飞书文档

改的是飞书云文档时要注意：标题层级改不了类型只能删了重建、空段落块不能传空数组、批量改的条数上限、以及改动带评注的段落会让评注脱锚。装了 `feishu-doc-ops` 的话，它的 `references/feishu-docx-block-editing.md` 末尾「Verified Gotchas — Long-Article Restructuring」一节有具体做法。

## 怎么汇报

- 诊断**按严重程度排**，不按发现顺序。结构问题排在语感问题前面。
- 每条给四样：问题是什么、具体在哪（引原句）、为什么是问题、怎么改。
- 结尾**只给一个推荐的下一步动作**，别一次抛一堆待决项。
- 改完要说清哪些没改、为什么（比如作者的归档编号、需要作者本人拍板的内容）。
