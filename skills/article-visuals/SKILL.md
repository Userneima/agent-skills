# 对外文章配图

## 适用范围

从给技术科普长文配图里总结出来的：文章发微信公众号，正文放在飞书文档里，说明图由另一个 agent 或脚本按简报画。封面那一节的尺寸是公众号后台的规格，其他平台按各自的规格来。

标着「默认做法」的地方是一种选择，后面写了理由，理由对你不成立就改。

## 先分清两类图，它们的任务是相反的

| | 正文说明图 | 封面图 |
|---|---|---|
| 任务 | 把一件事说清楚 | 在信息流里被点开 |
| 该克制吗 | 要，多余的视觉元素都是干扰 | 不要，克制的封面没人点 |
| 约束 | 默认做法：纯文字方块、无图标、无渐变 | 可以有视觉主体、层次、质感 |

说明图默认只用文字方块，理由是它要讲清一个关系，图标和渐变不帮忙讲清，还会在缩小之后糊成一团。文章本身视觉风格很重、需要配合的时候可以放开。

**把说明图的约束照搬给封面，必然出一张平淡的说明图。**这是最容易犯的错——写封面简报时会顺手复制正文的风格约束，结果封面就成了另一张插图。写之前先问自己：这张是要讲清楚，还是要被点开。

## 一、正文说明图：哪里配

**值得配的**：纯结构关系、文字要花三段以上才说清、读者容易卡壳的地方。判断依据不是「这段重不重要」，是「这段是不是在描述一个空间/层次/流转关系」。典型如：一换全换的替换关系、自下而上的层叠结构、谁调度谁的从属关系。

**配了有害的**：

- **标注为推测的章节**。配一张正经架构图会让推测看起来像已证实的事实，把作者辛苦划的那条线又抹掉。
- **图和紧跟其后的列表内容重复**。同一件事读者要读两遍。二选一：留图删列表，或者留列表删图。
- **没有稳定结构关系的段落**。事实陈述、人物脉络、清单，画出来只是把文字塞进方框。

**分布也要看**：图集中在前半篇、后半篇一张没有，读者会觉得后面在敷衍。

## 二、交出去：传达意图，只用约束划禁区

**约束能保证「不违规」，保证不了「做得好」。** 所以简报的主体是意图——这张图要让读者看见什么；约束只负责划禁区。反过来做（主体是规范、意图靠猜）必然返工。

四条要点：

1. **意图归你，版式归对方。** 你定：这张图要让读者看见的那件事、必须成立的关系（谁比谁多、什么形状、谁带动谁）、绝对不能出现的东西。对方定：构图、配色、字号、图标、留白、文字放多少。把「左中右三块」「12px 圆角」写死是越权，而且做出来会丑。
2. **关系约束 ≠ 版式指令。** 「左块要明显比右块窄」是关系（薄与厚是这张图的意思本身）；「左块用浅灰边框」是版式。曲线「两端高中间低」是研究结论，画成单调下降就是把结论画错——这类必须写。只写前者。
3. **上下限一起给，只给一端对方就滑到另一端。** 上限：解释性句子留给正文，图上放标签不放解释（标签＝识别这是什么的短词 2–12 字；解释＝为什么、怎么样的句子）。下限：**不许有空框**，每个框／箭头／区域都要有自己的标签，标签必须是完整词，不同元素的标签不能说同一件事。
4. **给多细取决于源头可不可信。** 正文没核实 → 逐字写死图内文字（让它从错的正文取词只会把错误画得更准）。正文已逐条核实 → 只给意图和禁区，词由它自己取（写死会连文字量一起写死，图变成排版成图片的文字墙）。所以第一步不是写要求，是先问「正文核完了吗」。

三个机制（不依赖对方或自己记住规则）：

- **能转述需求方原话就别自己转述。** 判断力附着在原话上：「图片很丑，完全没考虑美观」比任何一条美学规范都管用。可以直接用第一人称替需求方起草简报。
- **把自检推给对方**，写成一句可执行的：「画完把图上的字从头念一遍，有空框或读不通的词就是没画完」。
- **产出落点写明确**：存到指定路径，或直接插进文档指定位置。你必须能亲眼看到图，不能靠对方描述。
- **多张图一次给全**，并写明「必须同一套视觉语言」。分次给等于让对方每次重新定一套风格。

## 三、图会过期：出图前后都要核专有名词

**最难发现的图错不是画错，是画对之后过期了。** 图是静态图片：正文改了它不跟着改，而且它躲过所有针对正文的检查——**搜正文搜不到图里的字**。

- 出图前：图上每个专有名词（命令名、skill 名、字段名、接口名、版本号）回仓库核一遍还在不在、还叫不叫这个名字。核法 `git grep <名字> <tag>`、`gh api` 查目录、直接开链接看是否 404。
- 改正文时：只要动了某个专有名词，同步查有没有图也画着它。这一步最容易漏。
- 验收时：把图上文字全当待核事实，别因为「上次确认过」跳过。


## 四、验收：五件事，缺一不可

图回来别急着收，逐张核：

1. **关系有没有画反**——最常见的实质错误。典型是把「三个必须同时成立的条件」画成了一条先后箭头链。这类错误看着很专业，但意思是反的。
2. **标签有没有被改写**——模型很爱把「提供方」改成「服务提供者」，把原句润色一遍。跟正文逐字对。
3. **有没有冒出文章里没有的东西**——外部数据、别处的案例、自造的判断句。尤其警惕**无出处的图表**：正文对二手信息很谨慎，图里突然出现一条没标来源的曲线，会把全文的可信度一起拉下水。
4. **中文有没有糊**——出图模型最常见的失败，尤其括号里的小字。
5. **图里说的和正文说的是不是同一件事**——把图上每个专有名词当成待核事实，回仓库核一遍（见第三节）。**这一条是前四条抓不到的**：一张标签逐字照抄、关系没画反、没冒出新东西、中文清晰的图，内容仍然可以是错的——因为它照抄的是**已经过期的正文**。第四节讲的"图会过期"必须在这里落成一个动作，否则那一节只是提醒，不是检查。

**图能自己看**：从文档里把图下载下来直接读，不用靠用户描述。有问题就改简报重出，别自己动手改图。

## 五、位置：图要跟着内容走

**重排过段落之后，一定回头看图还在不在对的地方。**图片块不会跟着文字移动，段落一换顺序，图就错位了。

最常见的错位是**图出现在术语解释之前**——图上标着 bundle、Profile、Patch，读者还不知道这几个词是什么。规矩是：**先解释，再看图；图当小结，不当预告。**

## 六、公众号封面

**要两张，不是一张**：

- 信息流横图 `900 × 383`（2.35:1）
- 朋友圈转发方图 `500 × 500`（1:1）

后台可以分别上传。只传一张让微信自动裁，会切掉画面两侧或上下——而**重点常常正好在被切的位置**。横图还有一条：某些场景会从中心裁成 `383 × 383`，所以核心视觉和文案都要落在正中间那个方形区里。

**封面文案不要重复标题**。标题会显示在封面旁边，重复等于浪费一次表达机会。用文章里那句最反直觉的话，通常是标题没说的那半句。

**视觉方向从文章自身找**，别从「科技感素材库」里找。文章里往往已经有现成的画面感——「把整台机器拆开」就该画工业爆炸图，「插槽里换一块」就该画插槽。这类手法天然不像 AI 出图，而且缩小到信息流尺寸后靠形状仍然读得出来，纯文字大字缩小了就是一坨灰。

**网上关于公众号封面的主流建议（人物夸张表情、震惊脸）不适用于技术长文**——那是泛娱乐号的打法，用在技术文章上只会显得不专业。

## 七、插图进飞书文档的操作坑

最要紧一条：**不要让出图方用并排栅格放两个候选**。飞书的栅格删不掉其中一列，媒体 token 也不能跨块复用，想留一张得整个栅格删掉重新上传，五步操作。要候选就分两次单独插整宽图片块。装了 `feishu-doc-ops` 的话，它的 `references/feishu-docx-block-editing.md` 末尾「Verified Gotchas」有其余的坑。
